# asn1c-runtime

`asn1c-runtime` is the safe Rust runtime crate for Rust code generated by
asn1c. It provides primitive BOOLEAN, NULL, bounded signed `i64` INTEGER,
direct ENUMERATED, OBJECT IDENTIFIER, RELATIVE-OID, OCTET STRING, and BIT STRING
operations in selected combinations of UPER, APER, OER, CER, DER, and BER. This
is bounded coverage, not a complete ASN.1 codec implementation.

The crate also has JER encode/decode functions for BOOLEAN, NULL, finite
bounded signed `i64` INTEGER, direct nonextensible ENUMERATED, and fixed-size
OCTET STRING and BIT STRING plus bounded-size OCTET and BIT STRING.
ENUMERATED root names encode as compact quoted JSON strings; OCTET STRING
values encode as quoted uppercase hexadecimal, and bounded BIT STRING values
include their exact logical length in the C-compatible object form. Their decoders
accept one complete token with JSON whitespace around it and reject unknown
names, escapes, malformed hex, incorrect fixed sizes, trailing values, and
out-of-range bounded sizes or exhausted input, output, or work limits. The
primitive decoders report
consumption of the entire supplied input.
`-0` decodes as zero; integer output uses minimal decimal notation. JER does
not yet provide streaming or constructed-value codecs. Consumers that
represent JSON numbers as floating point should verify that their chosen
parser preserves the full signed 64-bit range.

The crate uses Rust 2021 and only the standard library. It forbids unsafe Rust.
Input, output, and bit-work limits are caller-configurable through `Limits`;
the defaults are 1 MiB for input, 1 MiB for output, and 8 MiBits of work per
operation. CER and DER encoding use the output and work limits; input limits
apply to the entire supplied decode slice, including any unused suffix. BER
and strict CER decoding charge the TLV octets times eight against the work
limit. Prefix decoders report both meaningful bits and whole bytes consumed.

```rust
use asn1c_runtime::{decode_boolean, encode_boolean, encode_boolean_cer, Limits};

let limits = Limits::default();
let encoded = encode_boolean(true, &limits)?;
assert_eq!(encoded.bytes, [0x80]);
assert_eq!(encoded.bit_len, 1);

let decoded = decode_boolean(&encoded.bytes, &limits)?;
assert!(decoded.value);
assert_eq!(decoded.consumed_bits, 1);

let cer = encode_boolean_cer(true, &limits)?;
assert_eq!(cer.bytes, [0x01, 0x01, 0xff]);
assert_eq!(cer.bit_len, 24);
# Ok::<(), asn1c_runtime::Error>(())
```

For PER, `Encoded.bit_len` excludes final-byte padding. BOOLEAN decoding reads the most
significant bit and preserves the C decoder's permissive handling of the
remaining padding bits. A complete zero-width UPER value is represented by one
zero byte with `bit_len == 0`; decoding an empty slice requests more input, and
a nonzero zero-width byte is invalid. Constrained INTEGER decoding rejects
spare bit patterns outside the declared range. CER results contain complete
TLV bytes, so `bit_len` equals `bytes.len() * 8`. The runtime exposes
`encode_boolean_cer`, `encode_null_cer`, and `encode_integer_cer`, plus strict
`decode_boolean_cer`, `decode_null_cer`, and `decode_integer_cer`. The decoders
require the exact universal tag and a short-form definite length (long-form
and indefinite lengths are rejected), BOOLEAN content `00` or `FF`, empty NULL
content, and 1 to 8 minimal two's-complement INTEGER octets within the bounds;
invalid bounds are reported first. Trailing bytes are left unconsumed, and
`consumed_bytes`/`consumed_bits` describe the TLV. Generated Rust wrappers
expose `encode_cer` and `decode_cer` methods when CER is selected.

`encode_*_aper` and `decode_*_aper` provide aligned PER primitive prefixes.
Each call begins at an octet boundary; the APIs do not compose fields inside
constructed values. APER BOOLEAN uses one meaningful bit, NULL and singleton
INTEGER use one zero filler octet with zero meaningful bits. Bounded INTEGER
applies the aligned range thresholds and checks spare codes. `encode_*_oer`
and `decode_*_oer` provide
octet-aligned primitive prefixes. OER BOOLEAN emits `00`/`FF` and accepts any
nonzero truth octet on decode; NULL uses an empty prefix. OER INTEGER encodes
the value itself in the fixed signed or unsigned 1, 2, 4, or 8-octet width
selected by its finite bounds. These operations enforce the same configurable
input, output, and work limits as the existing primitive APIs. Generated
wrappers expose `encode_aper`/`decode_aper` and `encode_oer`/`decode_oer` when
the corresponding `-gen-*` option is selected.
The aligned integer thresholds follow [ITU-T X.691 (2021)](https://www.itu.int/rec/T-REC-X.691/en),
and the fixed OER integer widths follow [ITU-T X.696 (2021)](https://www.itu.int/rec/T-REC-X.696/en).

`UperWriter` and `UperReader` compose direct BOOLEAN, NULL, finite bounded
`i64` INTEGER, fixed OCTET STRING, and fixed BIT STRING fields into one
continuous UPER value. They enforce the input
size once for the complete supplied slice, check output growth against the
complete output limit, and charge `max_work_bits` cumulatively: each field
costs its meaningful wire bits plus eight work units. NULL and singleton
INTEGER fields therefore still consume budget despite using zero wire bits.
The cursors add or check the one-byte zero-width filler only when finishing
the complete value. A failed field operation leaves the logical cursor
position and work count unchanged. Generated Rust uses these cursors for
flat SEQUENCE types when UPER is the only selected codec.
The string cursor methods validate exact lengths, require zero unused low BIT
STRING bits on write, and preserve bit position across field boundaries.

`encode_boolean_der`, `encode_null_der`, and `encode_integer_der` emit canonical
primitive TLVs. Their bytes match CER for this subset. `decode_boolean_ber`,
`decode_null_ber`, and `decode_integer_ber` read one definite-length universal
primitive TLV and report prefix consumption. BER decoding accepts long-form
lengths, including redundant leading length octets, and any nonzero BOOLEAN
content octet as true; empty or all-zero content is false. This matches the C
BER decoder's empty and multi-octet behavior, which extends X.690's one-octet
BOOLEAN content rule. CER still requires one canonical BOOLEAN octet. Primitive
indefinite lengths are rejected. INTEGER decoding accepts redundant leading sign
octets when the value still fits `i64`; that acceptance follows the C decoder
but extends the X.690 INTEGER wire rule. The generator exposes `encode_der` and
`decode_ber` only when `-gen-BER` is selected.

The BER module also exposes `encode_enumerated_der` and
`encode_enumerated_cer` for direct numeric `i64` ENUMERATED values, plus
`decode_enumerated_ber` and strict `decode_enumerated_cer`. OCTET STRING APIs
are `encode_octet_string_der`/`encode_octet_string_cer` and
`decode_octet_string_ber`/`decode_octet_string_cer`; BIT STRING has the same
suffix set and uses `BitStringValue` to preserve the exact bit count. BER
string decoding flattens primitive and constructed fragments with definite or
indefinite lengths. The checked parser accepts high-tag BER identifiers,
including nonminimal forms, and validates nested EOC framing to a fixed initial
depth cap of 30. CER encodes string contents through 1000 octets as primitive;
larger values use indefinite constructed form with 1000-content-octet
fragments (BIT STRING fragment content includes its unused-bit count). Strict
CER string and ENUMERATED decoding parses BER then compares against canonical
re-encoding. BER BIT STRING decoding masks unused low bits for C compatibility;
strict CER rejects noncanonical padding through that re-encoding comparison.
Constructed BER BIT STRING also requires every non-final fragment to have zero
unused bits. The runtime rejects a malformed form that the C BER decoder
accepts, following the X.690 fragment rule; strict CER rejects it as well.
The parser charges traversal and fragment-copy work incrementally, and strict
CER shares the same work ceiling across parsing, fragment copies, canonical
re-encoding, and byte comparison. SIZE constraints remain the generated type's
responsibility.

`BigInteger` stores a nonempty, minimal signed big-endian two's-complement
value. `BigInteger::try_from_signed_bytes` accepts redundant leading `00` or
`ff` sign-extension bytes and removes them; `as_signed_bytes` borrows the
canonical bytes, and `try_to_i64` returns `None` when the value is wider than
the signed 64-bit range. `encode_big_integer_der` and
`encode_big_integer_cer` emit a shortest primitive universal INTEGER TLV.
`decode_big_integer_ber` accepts redundant sign padding, nonminimal universal
high-tag aliases, and nonminimal definite length octets, then reports exact
prefix consumption. It rejects empty INTEGER content deliberately, although
the C wide INTEGER BER decoder accepts an empty content octet sequence. The strict
`decode_big_integer_cer` compares the consumed prefix with its canonical
re-encoding using one cumulative input, retained-value, scratch, output, and
work budget; it does not validate a suffix as part of the INTEGER value.

Flat BER/CER-only SEQUENCE and SET records can use one direct unconstrained
INTEGER through `FieldKind::BigInteger` with typed `write_big_integer` and
`read_big_integer` methods. This descriptor shares universal tag 2 with the
bounded `FieldKind::Integer`, while keeping their APIs and value constraints
separate. Record operations require `RecordContext::new_with_aggregate_scratch`
even when an optional `BigInteger` is absent. Record BER parsing and sign
normalization, retained allocation, canonical writing, and strict CER comparison
share the same context budget. Record encoding accounts output and runtime-owned
temporary storage; it does not charge unused reserve capacity in the caller's
borrowed `BigInteger` value. Record BER deliberately rejects empty and
constructed INTEGER forms, a narrower policy than C BER; C accepts empty
content.

`ObjectIdentifier` and `RelativeOid` retain opaque canonical base-128 content
octets, so subidentifiers are not limited to machine-sized integers. Their
fallible `try_from_content` constructors remove redundant leading `80` groups
from each arc, reject empty content and unterminated arcs, and expose canonical
content through `as_content`. The standalone
`encode_object_identifier_der`/`encode_object_identifier_cer`,
`decode_object_identifier_ber`/`decode_object_identifier_cer`,
`encode_relative_oid_der`/`encode_relative_oid_cer`, and
`decode_relative_oid_ber`/`decode_relative_oid_cer` functions use primitive
universal tags 6 and 13 with shortest definite lengths. BER accepts
C-compatible high-tag aliases and redundant base-128 leading groups, then
normalizes content. Strict CER rejects those aliases by comparing against the
canonical re-encoding under one cumulative work and scratch budget. Rust
deliberately rejects empty and unterminated BER contents even though the C BER
decoder accepts them; such content cannot represent a valid OID value.

Flat BER/CER-only SEQUENCE and SET records can use one direct OBJECT IDENTIFIER
and one direct RELATIVE-OID field through `FieldKind::ObjectIdentifier` and
`FieldKind::RelativeOid`, with typed `write_*` and `read_*` methods. These
natural fields require `RecordContext::new_with_aggregate_scratch`, even when
an OPTIONAL OID is absent. Record BER accepts primitive tag aliases and
normalizes redundant base-128 groups using the parent's shared work and
retained-capacity accounting. Constructed OID fields, empty content, and
unterminated arcs are rejected. Record DER/CER output uses primitive definite
TLVs; SET writers sort by universal tag while BER SET readers accept any
member order. Strict CER re-encoding and prefix comparison reuse the same
record context and include retained OID capacity plus output scratch.

`Ia5String` owns raw bytes and exposes them through `as_bytes`; its fallible
`try_from_bytes` constructor preserves all octets without checking the IA5
repertoire. `encode_ia5_string_der` and `decode_ia5_string_ber` likewise retain
arbitrary bytes, matching the C BER/DER callbacks. CER encoding and strict CER
decoding validate that every byte is at most `0x7f`; the entire 7-bit range,
including NUL and ESC, is accepted. BER constructed values use universal
OCTET STRING tag 4 fragments under outer IA5String tag 22. CER is primitive
through 1000 content bytes, then uses an indefinite constructed tag-22 value
with 1000-byte tag-4 fragments. Empty `16 00` is valid. BER also decodes an
empty constructed value, which strict CER rejects because its canonical form
is primitive `16 00`.

`CharacterStringKind` and `CharacterString` provide the same checked BER/DER/CER
operations for direct untagged ObjectDescriptor, UTF8String, NumericString,
PrintableString, TeletexString/T61String, VideotexString, GraphicString,
VisibleString/ISO646String, GeneralString, UniversalString, and BMPString roots.
The aliases preserve their requested kind while sharing universal tags 20 and
26. The generic value stores raw bytes; BER decode and DER encode do not apply
the CER checks. CER validation follows the C runtime: NumericString accepts
space and digits, PrintableString its ASN.1 alphabet, VisibleString bytes
`0x20..=0x7e`, IA5String bytes through `0x7f`, BMPString content lengths
divisible by two, and UniversalString content lengths divisible by four.
ObjectDescriptor, Teletex/T61, Videotex, Graphic, and GeneralString accept
arbitrary bytes under the C descriptors' no-op constraints. UTF8String mirrors
the C runtime's minimal 1- through 6-byte sequence validator, including legacy
5/6-byte forms and values outside Unicode scalar range; Rust `str::from_utf8`
would reject some C-accepted values. These are C compatibility rules rather
than broad claims about X.690 character repertoire validity.

Generic character strings use their own universal tag and universal OCTET
STRING tag 4 child fragments. CER stays primitive through 1000 content bytes,
then uses 1000-byte fragments. UTF8 validation runs after BER reassembly, so a
sequence may cross a fragment boundary. Strict CER re-encoding and comparison
share cumulative input, output, work, and scratch limits.

`UtcTime` owns raw UTCTime content bytes. Its fallible constructor and
`as_bytes` accessor do not apply time syntax checks. `decode_utc_time_ber` accepts
primitive or nested constructed tag-23 values with universal tag-4 fragments,
preserves the raw content, and reports exact prefix consumption;
`encode_utc_time_der` preserves those bytes in primitive tag 23. CER encoding
validates the permitted 11/13/15/17-byte forms, Gregorian date and clock,
1950/2049 year pivot, and numeric zone, then converts to UTC and writes exactly
`YYMMDDhhmmssZ`. Strict CER decoding re-encodes and compares only the consumed
prefix. Calendar conversion uses checked Gregorian arithmetic, so the valid UTC
instant 1969-12-31 23:59:59 is accepted even where the C `time_t == -1` sentinel
rejects it. Input, output, retained capacity, scratch, and cumulative work limits
apply to the UTCTime operations.

`GeneralizedTime` owns raw content bytes and exposes them through `as_bytes`;
its fallible constructor and BER decoder preserve arbitrary bytes. BER accepts
primitive or nested constructed tag-24 values with universal tag-4 fragments.
DER and CER encoding require an explicit `Z`, `+hh`, `-hh`, `+hhmm`, or `-hhmm`
zone, validate year 0001 through 9999 and Gregorian date/clock fields, then
normalize to UTC primitive tag 24. Optional minute and second pairs are
completed with zeroes; a fraction is allowed only after seconds, with one to
nine digits and either `.` or `,`. Canonical output uses full seconds, `Z`, a
decimal point, and trims trailing fractional zeroes; an all-zero fraction is
omitted. Strict CER decoding compares the normalized encoding with exactly the
consumed prefix. The deterministic Rust DER subset rejects local-time input,
invalid-date normalization, and fractions longer than nine digits; C may
interpret those using process timezone, normalize fields, or truncate precision.
Rust also accepts the valid 1969-12-31 23:59:59 UTC instant that C can reject
through its `time_t == -1` sentinel. GeneralizedTime operations use the shared
input, output, retained-capacity, scratch, and cumulative work limits.

`CollectionRootKind`, `CollectionElementKind`, `CollectionInput`, and
`CollectionValues` support direct top-level SEQUENCE OF and SET OF BOOLEAN,
NULL, or finite bounded `i64` INTEGER values. `encode_collection_der` and
`encode_collection_cer` borrow typed values; `decode_collection_ber` and strict
`decode_collection_cer` return owned typed values with exact prefix consumption.
SEQUENCE OF preserves its order. SET OF sorts complete canonical child TLVs by
zero-padded octet order; BER decode accepts any SET OF order and duplicates.
CER uses indefinite constructed roots with EOC, and strict CER compares the
canonical re-encoding against exactly the consumed prefix under one work
budget. INTEGER bounds are checked during Rust BER decode, earlier than C's
later constraint check. The runtime caps collections at 1,000,000 elements and
accounts decoded vectors, radix buffers, and output against a fixed 128 MiB
aggregate scratch ceiling without adding fields to `Limits`.

`ChoiceAlternative` and `ChoiceValue` describe a direct untagged CHOICE with
one through three uniquely tagged BOOLEAN, NULL, and/or bounded `i64` INTEGER
arms. `encode_choice_der` and `encode_choice_cer` emit only the selected
primitive TLV; `decode_choice_ber` and strict `decode_choice_cer` dispatch by
its universal tag and report exact prefix consumption. BER accepts C-compatible
high-tag and long-length aliases, empty or multi-octet BOOLEAN contents, and
redundant INTEGER sign octets. NULL still requires empty primitive content.
Strict CER re-encodes and compares the consumed prefix with one cumulative
work budget. The descriptor slice and selected arm are checked before parsing
or allocation. Bounded INTEGER values are range-checked during Rust BER decode,
which may occur earlier than C's later constraint check. Tagging, extensions,
and constructed CHOICE alternatives are outside this direct gate.

`ChoiceField`, `ChoiceAlternative`, and `ChoiceValue` support one inline
primitive CHOICE slot in an untagged flat SEQUENCE or SET. Natural SEQUENCE and
SET choices map all distinct BOOLEAN, NULL, or bounded INTEGER tags to one
logical field index; receiving two alternatives in one record is a duplicate.
`SequenceWriter::write_choice` and `SetWriter::write_choice` write the selected
value through the parent's shared record context. Readers use
`new_tagged_with_choice` and `read_choice`, accepting arbitrary SET member order.
For a natural CHOICE in SET, DER ordering uses the selected arm's wire tag, while
CER ordering uses the minimum tag among declared arms; the wire tag still
controls collisions and duplicate detection. EXPLICIT wrappers contain exactly
one declared primitive child and use definite DER or indefinite CER framing.
Schema collisions are rejected before parent parsing, and strict CER callers
re-encode with the same `RecordContext` before calling `verify_canonical` on
the consumed prefix. Required/OPTIONAL presence remains the generated wrapper's
responsibility. Nested alternatives and multiple CHOICE slots remain outside
this gate.

`RecordContext`, `SequenceReader`, `SequenceWriter`, `SetReader`, and `SetWriter`
compose flat SEQUENCE and SET values with direct BOOLEAN, NULL,
ENUMERATED, bounded INTEGER, and bounded BIT/OCTET STRING fields under one
input/output/work budget. Supply the unique universal field tags to a reader;
`next_field` advances one field and the matching `read_*` method consumes it.
SEQUENCE tags are supplied in declaration order and BER members must follow
that order. SET accepts arbitrary BER member order and rejects unknown or
duplicate tags. Optional/default omissions are represented by absent tags,
while generated code checks required fields and omits values equal to DEFAULT.
Both readers' `finish` methods require the definite boundary or matching EOC to
have been read. Writers use definite DER or indefinite CER outer framing;
SEQUENCE fields follow declaration order, while SET fields must be written in
ascending effective-tag order. `RecordContext::verify_canonical` charges the
final byte comparison after callers re-encode with that same context. This
record API accepts at most six fields with unique effective tags. During
decode, `max_output_bytes` also caps aggregate retained BIT/OCTET/IA5
payload bytes across fields. DER string fields are primitive; CER uses
1000-content-octet fragments, counting the BIT STRING unused-count octet.
Other tagged record containers, extensions, and deeper record trees remain
outside this slice.

Flat records also support natural, unconstrained `IA5String` fields through
`FieldKind::Ia5String`, `write_ia5_string`, and `read_ia5_string`. BER and DER
preserve arbitrary content bytes. CER validates every byte is at most `0x7f`;
values through 1000 bytes are primitive, and larger values use constructed
tag 22 with universal OCTET STRING tag-4 fragments. Record readers flatten
definite or indefinite BER fragments and retain their allocation in the shared
context for strict CER re-encoding. IA5-containing generated operations use
`RecordContext::new_with_aggregate_scratch` even when the field is OPTIONAL and
absent. This enables the 128 MiB retained-plus-record-output scratch cap while
leaving nested-record callbacks disabled; public IA5 reader/writer methods
reject contexts created with `RecordContext::new`. Record field accounting
includes decoded IA5 capacity and record-owned output buffers; it does not add
the capacity of a caller-owned IA5 input value. Direct top-level IA5 codecs use
their own simultaneous value-plus-output scratch accounting.

Flat records also support one natural restricted character-string field with
FieldKind::CharacterString(kind), write_character_string(kind, value), and
read_character_string(kind). The value kind must exactly match the descriptor,
so Teletex/T61 and Visible/ISO646 aliases retain their declared identity even
when they share a wire tag. The generic record API excludes IA5String, which
continues through its source-compatible FieldKind::Ia5String methods.

The character-string field uses the same flat RecordContext for BER fragment
flattening and strict CER re-encoding. Its descriptor requires aggregate-scratch
mode even when OPTIONAL is absent. Writers validate the C descriptor repertoire
before CER commit and fragment values above 1000 content octets as universal
tag-4 children; BER readers accept definite or indefinite nested tag-4 fragments
and retain their capacity incrementally against the 128 MiB aggregate cap.
CER validation runs after complete reassembly, including UTF8 sequences split
across fragment boundaries. As with IA5 fields, record accounting includes
record-owned decoded capacity and output but not caller-owned input capacity.

For a flat SEQUENCE root with one context-specific IMPLICIT tag, use
`SequenceReader::new_tagged_root(input, tag, fields, context)` and
`SequenceWriter::finish_tagged_root(tag)`. These operations validate the root
tag against the C runtime's `0x3fff_ffff` ceiling, require a constructed wire
identifier, preserve the exact BER prefix length, and use the same record
context for strict CER re-encoding. BER accepts C-compatible nonminimal high
tag identifiers; canonical CER uses the shortest identifier and indefinite
outer length. The root API preserves `RecordContext::new` flat-record resource
behavior, including checked output and work for identifier growth.

Flat SET roots support the same single context-specific IMPLICIT tag through
`SetReader::new_tagged_root(input, tag, fields, context)` and
`SetWriter::finish_tagged_root(tag)`. The writer keeps SET components in
ascending effective-tag order, while the BER reader accepts any member order.
Strict CER validation re-encodes with the same context, so reversed member
order is rejected as noncanonical. For [3] IMPLICIT SET with [0] INTEGER 2
and [1] BOOLEAN TRUE, DER is `a3 06 80 01 02 81 01 ff` and CER is
`a3 80 80 01 02 81 01 ff 00 00`.

The record API also supports fixed effective tags with a separate `FieldKind`
through `RecordField`, `Tag`, and `TagClass`. `SequenceReader::new_tagged` and
`SetReader::new_tagged` borrow up to six checked descriptors; their typed
`read_*` methods validate the descriptor kind, and `next_tagged_field` returns
class and number without conflating tags. Writers provide corresponding
`write_*_tagged` methods while preserving the universal-only methods. Tags may
use Universal, Application, ContextSpecific, or Private classes and numbers up
to `0x3fff_ffff`, matching the C runtime's packed tag range. BER accepts
nonminimal high-tag identifier aliases, including redundant leading zero
groups, within input and work limits; DER/CER writers emit minimal high-tag
identifiers. SET writer order compares class then number. For IMPLICIT
BIT/OCTET STRING, the effective tag replaces only the outer tag; CER and BER
constructed string fragments retain universal component tags 3 and 4.
`RecordField::new_explicit` adds a context-specific EXPLICIT mode without
changing the implicit constructor. The corresponding `write_*_explicit`
methods wrap one intrinsic universal child; DER uses a definite wrapper and
CER uses an indefinite wrapper with EOC. Readers accept definite or indefinite
BER wrappers, require exactly one matching universal child, and charge wrapper
parsing, child decoding, and strict CER re-encoding to the same record context.
Explicit BIT/OCTET STRING children use their regular universal primitive or
fragmented CER form inside the wrapper.

The record API supports sequential SEQUENCE or SET child callbacks inside a
flat SEQUENCE or SET. Each child may use its natural tag, one IMPLICIT tag, or one
context-specific EXPLICIT wrapper, and contains up to six direct supported
primitive members. Generated required/OPTIONAL checks remain type-specific.
`write_nested_sequence`/`read_nested_sequence` and
`write_nested_set`/`read_nested_set` use callbacks so each child shares its
parent's `RecordContext`; child decoding receives only the validated inner TLV
span and must consume that span exactly, including its own EOC. BER child SET
members may arrive in any order; DER/CER child SET output uses effective-tag
order. A failed read callback rolls the parent cursor and field-seen state back
to the nested field start. Work and decoded-allocation charges remain
cumulative after failure, even if a decoded value is dropped; callback side
effects and captured values are not rolled back.
BER accepts independently definite or indefinite parent, EXPLICIT-wrapper, and
child lengths when each boundary and EOC is correctly matched. Strict CER
rejects noncanonical mixed forms through canonical re-encoding comparison.
DER writes definite nested lengths; CER writes indefinite nested records and
EXPLICIT wrappers. SET output order uses each child's outer effective tag.

Nested record callbacks are limited to one active child level. Completing or
failing one child releases that active level before the next sibling enters;
the parent's work and allocation accounting continues across both callbacks.
The generator currently validates one or two direct named record children;
see the compiler support matrix for its schema restrictions. Generated operations
for schemas containing a child use `RecordContext::new_nested` from the public
operation boundary, even when an OPTIONAL child is absent. `RecordContext::new`
retains the existing flat-record behavior, and nested callbacks fail closed
when used with that flat context.
Direct imported record children use the same callbacks through crate-visible
generated field helpers. Their source module supplies the type, while the
parent retains the shared work, allocation, scratch, input, and output limits.
No additional runtime nesting level is introduced by the module boundary.

A generated directly imported bounded INTEGER field uses these same scalar
record readers and writers. Its source module supplies the checked newtype;
its parent supplies the operation context. Crossing the module boundary does
not start a new input, output, allocation, or work budget.

A generated transparent local INTEGER alias uses its direct base's checked
Rust type and public codecs. In a record, the declared alias name is retained
for field storage and construction, while the same parent readers and writers
enforce the base range. Alias resolution adds no runtime context or nesting.

The opt-in nested context caps live parent/child record-buffer capacities plus
cumulative decoded string-buffer capacity charges at 128 MiB. Charges are
conservative and remain after a failed callback because its values may have
escaped through callback side effects. This fixed scratch cap is separate from
`max_output_bytes`, which continues to bound complete encoded output and
cumulative decoded payload lengths. Capacity rounded above the requested
length counts against the scratch ceiling. Projected sizes are checked before
allocation; actual capacities are checked immediately after reservation and
before the parent field commits. Child parsing, encoding, and canonical
comparison use the same operation work budget.

CBOR primitive APIs encode BOOLEAN, NULL, bounded signed INTEGER and opaque
ANY. They decode one definite prefix, accept leading semantic tags and
nonminimal definite heads, and reject INTEGER bignum tags and indefinite byte
strings. ANY is represented as a definite CBOR byte string and is limited to
`INT32_MAX` octets for compatibility with the C `ANY_t` size field.

`cbor::encode_map` and `cbor::decode_map` support generated flat SEQUENCE
values as definite text-key maps. The encoder preserves entry order and rejects
duplicate keys or non-complete CBOR values. The decoder accepts leading tags
and nonminimal definite heads, rejects duplicate keys, and returns borrowed
complete value spans. Unknown definite nested values can be skipped up to 64
levels; indefinite items and invalid UTF-8 text keys remain unsupported. The
generated decoder validates
each known value consumes its entire span and checks required members.

Direct fixed or bounded OCTET STRING values use definite CBOR byte strings.
BIT STRING values add one leading payload octet for the unused-bit count,
matching C; the decoder checks exact meaningful bit length and zero padding.
Both paths enforce the declared SIZE range and caller resource limits.

Generated CBOR CHOICE values use one-entry text-key maps. Top-level typed
CONTAINING wrappers place complete inner BOOLEAN or bounded INTEGER CBOR bytes
inside those BIT/OCTET string encodings; BIT contents must be octet aligned.
The narrow IOC-selected OPEN TYPE uses a two-field SEQUENCE map with the
selector and a direct selected CBOR value. Decoding accepts either field order,
skips unique unknown keys, rejects duplicates and missing fields, and checks
the selected value consumes its full encoded span.

The XER writer supports bounded basic XML output for generated flat SET and
SEQUENCE records. The generator currently accepts BOOLEAN, bounded INTEGER,
unconstrained IA5String fields, and REAL DEFAULT 0.5 with finite limited values only. XER decoding is not implemented.
IA5 C0 controls other than tab, line feed, and carriage return are rejected;
REAL values must survive a round trip through the emitted decimal text.
